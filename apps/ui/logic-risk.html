Risk controls are a prerequisite for a viable solution: who may read business data, write shared info, and initiate outreach must be approvable, verifiable, and traceable. Boundaries also clarify what this phase delivers so it is not read as “every planned feature is already live.”

Governance and compliance

Data and tool permissions

  • Tools grouped as: read business data / search knowledge base / write shared and gate
  • Each feature may only use approved-scope capabilities; no private dept data bypass
  • Master data and metric definitions use a single entry point

Shared write and outreach red lines

  • Shared writes must declare producer and allowed consumer scope
  • Renewal outreach must check shared complaint info first
  • When outreach is deferred, keep the reason for audit

Run traceability

  • Each run keeps id, loop type, feature name, and step log
  • Ops console can view metrics, related changes, and handling chain
  • Cross-dept collaboration relies on shared info, not verbal handoffs

Human–AI responsibility

  • Collaborative: AI assists; business owns external outcomes
  • Approval: high-risk writes and outreach cannot auto-pass silently
  • Reporting: risk signals enter shared layer; rules or humans decide consequences

Boundaries

Architectural non-goals

  • One universal chat entry for everything
  • Each dept building isolated AI with private data access
  • Treating “one shared persona” as cross-dept collaboration solved
  • Multi-role auto handoff as the default collaboration pattern

This phase scope

  • Qingshu Mobility is a portfolio reference implementation, not a production customer delivery
  • Outbound lines, agent QA engines, line vision, etc.: planned features, phased delivery
  • Phase 1 proves: multiple loop types run, shared info is consumable, outreach is gated, runs are observable
  • Demo data is synthetic; no real customer contracts or raw ticket text
